# Reference implementation

This folder contains an isolated, pedagogical Python reference slice for the adaptive response filtering idea described in the production investigation article. The repository is a documentation-led engineering knowledge base, not an operational Agentic AI service or a production-ready transport framework.

The goal is to make selected policy, chunking, envelope, and reassembly behavior concrete enough to inspect and test. It does not include a model runtime, HTTP server or writer, network gateway, browser or TypeScript client, progressive UI, timeout scheduler, receiver observability, or deployment infrastructure. Session retry and full-buffer fallback are implemented as caller-driven callbacks; envelope authentication does not provide transport or user authentication. The article's production workflow and measurements are not generated by this code, and the local demo is not a reproduction of those benchmarks.

This implementation is intentionally constrained in exactly the same way the article describes: the entire response is serialized before the first yielded chunk or envelope, and the local wire contract is purposely bounded to a small message-scoped protocol. That is a deliberate teaching choice to keep the example readable, easy to test, and easy to reason about. It is not a production transport implementation and it is not meant to stand in for an application server or an end-to-end networked system.

- [adaptive-response-filter/reassembler.py](./adaptive-response-filter/reassembler.py) — bounded single-message receiver and reassembly logic
- [adaptive-response-filter/demo.py](./adaptive-response-filter/demo.py) — a simple script that demonstrates the full-buffer and chunked paths

Chunk envelopes use CRC32 for accidental-corruption detection and HMAC-SHA256 for envelope integrity. The payload and metadata are authenticated with a caller-supplied shared key, so the receiver rejects tampered chunks that do not match the expected key. This is not transport or user authentication. Object fragments carry `merge_mode="json-object"` and are merged by key; text, arrays, and other serialized values use `merge_mode="concat"` and are restored byte-for-byte. UTF-8 chunks stay on code-point boundaries. A top-level JSON element that cannot fit by itself raises `UnsplittableValueError` instead of exceeding the configured cap.

This implementation is not an operational AI service. It is a pedagogical Python reference frame for a response-delivery protocol idea. It does not implement a model runtime, an HTTP server, a browser client, a database-backed queue, streaming UI behavior, or a full network security boundary. It exists to demonstrate the contract, validation, chunking logic, and reassembly constraints in a small and inspectable form.

This boundary is intentional. The repository does not ship an agent platform, gateway, transport layer, UI runtime, queue, persistence layer, or production key-management system. The local Python slice is intentionally restricted to a message-scoped protocol exercise. That makes the invariants easy to reason about: one `Reassembler` per message, a session manager with caller-driven retry and full-buffer fallback callbacks, stable chunk metadata, CRC32 as corruption detection, HMAC-SHA256 as envelope integrity, and explicit rejection of invalid or conflicting fragments. No timeout scheduler or receiver observability is included.

Chunk and threshold limits are validated before use. A `Reassembler` instance handles one message only, with defaults of 10,000 chunks and 16,000,000 reassembled bytes; it rejects changing chunk totals, invalid sequence indexes, conflicting duplicate frames, and reuse after completion. A `ReassemblySession` can request missing chunk indexes and, after a configured retry budget, invoke a caller-provided full-buffer callback; it does not render partial results itself. Create a new instance for each message and treat the implementation as a local protocol exercise, not as a production transport or security boundary.

The receiver validates envelope structure, checksum, and HMAC with a shared key before accepting a chunk. This remains an educational reference contract, not a production network security boundary. The deliberate simplifications are part of the design: small code, clear invariants, and explicit validation help readers reason about the wire contract without introducing unrelated runtime complexity.

## Contract limitations and deliberate simplifications

The educational wire contract is intentionally narrow. It is designed to make protocol reasoning simple, not to imitate a production message bus or secure transport layer. The most important limitations are:

- `CRC32` is used for accidental corruption detection; HMAC-SHA256 authenticates a caller-supplied shared key.
- Each `Reassembler` instance only handles one logical message; it does not queue multiple concurrent streams or manage retransmissions.
- `ReassemblySessionManager` supports interleaved message sessions and callback-driven retry/fallback, but does not schedule polls or provide receiver observability.
- `total_chunks` and sequence indexes are treated as strict message metadata; a change in those values after the message starts is rejected.
- Duplicate frames are tolerated only when the payload is identical; conflicting duplicates are rejected rather than silently merged.
- UTF-8 boundaries must remain valid; a payload that cannot be split cleanly within the configured byte cap raises `UnsplittableValueError`.
- The implementation does not include production key provisioning, storage, rotation, transport confidentiality, persistence, or delivery guarantees beyond local validation and bounded state management.

Those choices are deliberate and should be treated as part of the teaching model, not as a gap in the implementation of an unbuilt system.
